# medogen — генератор тестовых пакетов МЭДО 3.0, 2.7.1, 2.7 и 2.6 (и ниже)

Консольная утилита на Python. Пакеты описываются сценариями в JSON. Утилита собирает
готовые электронные сообщения (envelope.ini, message.xml, *.edc.zip; в 2.6 — document.xml и
файлы рядом) и сразу проверяет их по XSD.

- [Инструкция пользователя](docs/USER_GUIDE.md) — как работать в интерфейсе, для тестировщиков.
- [Сквозной тест для тестировщика](docs/TESTER_GUIDE.md) — исходящий из СЭД → OUT → квитанции и уведомления → ответ в IN.
- [Развёртывание на внутреннем сервере](docs/DEPLOY.md) — общий экземпляр для команды.
- Обмен с СЭД через папки OUT и IN — [инструкция пользователя, раздел 5](docs/USER_GUIDE.md#5-обмен-с-сэд-через-папки-out-и-in).
- Маршрутизация между стендами: пакеты из OUT одного стенда после проверки сами попадают в IN
  другого, ответы идут обратно — [раздел 6](docs/USER_GUIDE.md#6-маршрутизация-между-стендами).

Что умеет:

| Что | 2.7.1 | 3.0 |
|---|---|---|
| Исходящий документ (ТК «Документ в электронном виде») | `document` | `document` (TC00000002), с digital.xml или без |
| ТК «Цифровой документ ГосЭДО» | — | `gosedo` (TC00000007, digital.edc.zip) |
| Обращение гражданина | `citizen_appeal` (CardInfo.txt) | `citizen_appeal` (см. «Допущения») |
| Квитанция о приеме / отказе | `receipt` (acknowledgment) | `receipt` (resultAccept / resultReject) |
| Уведомления | `notification`: все 8 видов 2.7.1 | `notification`: регистрация / отказ в регистрации (digital.xml) |
| Цифровые поручения | `assignment`: digital.xml как приложение 101 | `assignment`: digital.xml в ТК ДЭВ или ТК ГосЭДО |

События поручений: выдача (`issue`), изменение срока (`change_deadline`), возврат доклада на
доработку (`return`), принятие информации об исполнении (`accept`), прекращение контроля
(`stop`).

Старые форматы:

| Что | 2.7 | 2.6 и ниже |
|---|---|---|
| Документ, обращение гражданина | `document`, `citizen_appeal` — ТК версии 2.7 (http://minsvyaz.ru/container) с подписью ТК, имена файлов как в эталоне «2.7. Входящее письмо» | `document`, `citizen_appeal` — без ТК: document.xml (заголовок «Документ», реквизиты, files) и файлы рядом |
| Квитанция | `receipt` (acknowledgment без кода ошибки) | так же, файл document.xml |
| Уведомления | `notification`: все виды 2.7.1, кроме «Поставлен на контроль» (`sent`); у отказа одна причина | так же, файл document.xml |
| Поручения, ТК ГосЭДО | нет в формате | нет в формате |

Для 2.6 можно указать версию ниже: `"format": "2.5"`, `"2.4"` и т.д. (от 2.0 до 2.6) — пакет
собирается по структуре 2.6, в атрибут `version` пишется выбранная версия.

## Установка

```
git clone https://github.com/Yaymko/Medogen.git medogen
cd medogen
```

Нужен Python 3.8 или новее. Для проверки по XSD установите lxml (без него пакеты
собираются, но проверяется только структура):

```
pip install lxml
```

## Быстрый старт

```
python medogen.py build examples
```

Можно запустить и `run_examples.bat`.

## Интерфейс для тестировщиков

```
python medogen.py ui
```

или `run_ui.bat`. Откроется страница http://localhost:8765 в браузере. Дополнительные пакеты
не нужны; lxml по-прежнему включает проверку по XSD. Остановить сервер: Ctrl+C в окне консоли.

Вкладки:
- **Создать пакет.** Выберите формат и тип, отправителя и получателей, заполните поля и
  нажмите «Собрать пакет». Отправителя и получателей можно взять из стенда или найти в
  справочнике ГАС (поле поиска под списком: название, адрес МЭДО или GUID). Справа появятся GUID (копируются по щелчку), состав пакета с
  просмотром любого файла, в том числе внутри ТК, результат проверки и кнопка «Скачать .zip».
  Кнопками «Ответный документ», «Квитанция», «Уведомление», «Событие по поручению» сразу
  готовится ответ на этот пакет. Ответный документ — исходящий документ от получателя
  входящего пакета его отправителю: в паспорт ТК добавляется связь «Связан с» с исходным
  документом (УУИД, номер, дата), краткое содержание по умолчанию «Ответ на № … от …».
  Ту же галочку «Ответный документ на входящий пакет» можно поставить у исходящего документа. «Показать JSON сценария» выдаёт тот же пакет в виде сценария для командной строки.
- **Пакеты.** Все собранные пакеты с поиском и фильтрами. Сюда же загружается входящий пакет
  из СЭД: архивом .zip, файлами (envelope.ini, message.xml, *.edc.zip), папкой или
  перетаскиванием. Пакет проверяется, и сразу открывается окно «Ответы пачкой»: отметьте
  нужные квитанции (о приёме, об отказе с причиной), уведомления (для 2.7.1 все виды, для
  3.0 регистрация и отказ) и ответный документ, укажите адрес МЭДО отправителя, если его нет
  ни в стенде, ни в ГАС, и
  нажмите «Сформировать ответы». Каждый ответ собирается отдельным пакетом с проверкой, все
  ответы можно скачать одним архивом.
- **Сценарии.** Запуск готовых сценариев из examples и своих .json.
- **Организации.** Справочник стенда: добавление и правка организаций, новый стенд. Здесь же
  загрузка справочника ГАС (сохранённая страница addresseesActual.html) и поиск в нём с
  добавлением организации в стенд. Стенд выбирается в шапке.

Пакеты интерфейса лежат в `out\ui`, входящие — в `out\ui\_incoming`.

Чтобы открыть интерфейс коллегам по сети, запустите `python medogen.py ui --host 0.0.0.0`
и дайте им адрес `http://<имя компьютера>:8765`. Авторизации нет, поэтому делайте так только
во внутренней сети. Пакеты появятся в папке `out\`, по одной папке на
пакет. В папке пакета лежат только файлы пакета: envelope.ini, message.xml и ТК (*.edc.zip).
Сгенерированные GUID (сообщения, документа, процесса поручения) записываются отдельно, в
`out\_manifests\<папка пакета>.json`: так их удобно искать в СЭД, а в пакет не попадают
лишние файлы.

Команды:

```
python medogen.py build <сценарий.json | папка> [--orgs orgs\стенд.json] [--out папка] [--zip]
python medogen.py build ... --orgs orgs\стенд.json --put in|out   собрать и положить в IN или OUT стенда
python medogen.py put <папка пакета> ... [--orgs orgs\стенд.json] [--to in|out]   положить готовый пакет
python medogen.py validate <папка пакета> ...       проверить любой пакет, в том числе чужой
python medogen.py import-orgs addresseesActual.html orgs\стенд.json --stand "Тестовый стенд"
python medogen.py import-gas addresseesActual.html  загрузить/обновить справочник ГАС (gas\gas.json)
python medogen.py gas Тюменская область            поиск в справочнике ГАС
python medogen.py orgs [--orgs orgs\стенд.json]     показать справочник
```

`--zip` дополнительно упаковывает каждую папку пакета в .zip. `--put` и `put` берут папки IN/OUT из раздела
`exchange` файла стенда и кладут только пакеты без ошибок проверки (как кнопки «Положить в IN/OUT»).

## Справочник организаций (GUID разные на разных стендах)

Организации хранятся в `orgs\*.json`, по одному файлу на стенд. По умолчанию берётся
`orgs\default.json`. В нём GUID из эталонных пакетов, названия и адреса МЭДО сверены с ГАС
ГосЭДО от 20.10.2026.

```json
{
  "stand": "Тестовый стенд 1",
  "self": "my_org",
  "orgs": {
    "my_org":  {"guid": "b72c0f24-d3dc-4cbf-8bfe-5da94daa18bf", "name": "Правительство Московской области", "address": "PRAVMO_S~MEDOGU"},
    "partner": {"guid": "0c52f66a-b3d2-4bd1-adcc-53637b20099f", "name": "Московская областная Дума", "address": "PRAVIT_MO_O~MEDOGU"}
  }
}
```

- `guid` — GUID участника из ГАС, пишется в паспорта.
- `address` — адрес МЭДО для раздела [АДРЕСАТЫ] в envelope.ini.
- `self` — отправитель по умолчанию, если в сценарии нет `from`.

Чтобы собрать те же сценарии для другого стенда, укажите другой справочник:
`--orgs orgs\stand2.json`. Сценарии ссылаются на организации по ключу (`"partner"`), так
что сами сценарии менять не нужно.

**Справочник ГАС ГосЭДО (`gas\gas.json`).** Общий справочник всех участников МЭДО. Сохраните
страницу https://gosedo.ru/wp-content/uploads/files/addresseesActual.html в браузере
(Ctrl+S) и выполните `import-gas` или нажмите «Загрузить / обновить справочник ГАС» на вкладке
«Организации». Страница хранит данные в упакованном виде (около 36 тыс. участников), генератор
распаковывает их сам. Повторная загрузка заменяет справочник целиком. В поставке лежат только
7 организаций примера.

Если организации нет в стенде, но её GUID есть в ГАС, название и адрес МЭДО берутся из ГАС:
в сценарии достаточно указать GUID (`"to": ["6d8c1ef5-a5ea-4dd9-a97d-5ee80f0663b1"]`). Это
работает и для ответов на входящие пакеты: адрес отправителя входящего находится по ГАС.

**Импорт в стенд.** `import-orgs` создаёт из той же страницы (или CSV «название; GUID; адрес»)
отдельный стенд со всеми активными участниками. Ключами станут первые 8 символов GUID.

В сценарии вместо ключа можно указать GUID или объект целиком:
`{"guid": "...", "name": "...", "address": "..."}`.

## Сценарий

Сценарий описывает один пакет или их список. Общие поля:

```json
{
  "settings": {"timezone": "+03:00", "time_limit": 240, "message_file": "message.xml",
               "subject": "Сообщение МЭДО", "sign_command": null},
  "defaults": {"format": "3.0", "from": "my_org"},
  "packages": [
    {"name": "doc", "type": "document", "to": ["partner"], "document": {...}},
    {"name": "ok",  "type": "receipt", "reply_to": "@doc"}
  ]
}
```

- `format` — `3.0`, `2.7.1`, `2.7`, `2.6` или ниже (`2.5`, `2.4`, … `2.0`). По умолчанию `3.0`.
- `type` — `document`, `gosedo`, `citizen_appeal`, `receipt`, `notification` или `assignment`.
- `from`, `to` — ключи организаций. Адресату можно указать должностное лицо:
  `{"org": "partner", "person": {"post": "Губернатор", "name": "..."}}`.
- `reply_to` — ответ на пакет (квитанция, уведомление). Значение `@имя` указывает на пакет из
  этого же сценария. Можно указать и путь к папке любого пакета, в том числе полученного
  от СЭД. Из пакета берутся msgUid, docUid, номер и дата документа, процесс регистрации,
  а также отправитель и получатель, поменянные местами.
- `based_on` — следующее событие по поручению. Из пакета выдачи берутся процесс, пункты,
  исполнители и соисполнители.
- Даты: `"today"`, `"today+30"`, `"today-1"` или `"2026-06-21"`.

### Раздел document (для document, gosedo, citizen_appeal, assignment)

```json
"document": {
  "kind": "DK00000000",                 // или {"id": "DK...", "name": "..."}
  "place": "DP00000077",
  "classification": "DC00000000",       // DC00000001 = ДСП, в 3.0 тогда secure=true
  "annotation": "О проведении мероприятий",
  "reg_number": "П-МО-96", "reg_date": "today",
  "pages": 2,                           // страниц в PDF-заглушке
  "pdf": "files\\письмо.pdf",           // свой PDF вместо заглушки
  "signer": {"post": "...", "name": "...", "id": "СНИЛС",
             "signature_file": "files\\sign.p7s", "stamp_file": "files\\stamp.png",
             "stamp": {"page": 1, "x": 74, "y": 255, "w": 41, "h": 18}},
  "signers": [ ... ],                   // несколько подписантов
  "executor": {"post": "...", "name": "...", "phone": "..."},
  "reg_stamp": {"page": 1, "x": 34, "y": 74, "w": 38, "h": 10},
  "links": [{"org": "partner", "number": "39", "date": "2025-06-26", "uid": "...", "type": "LT00000000"}],
  "attachments": [
    {"file": "files\\смета.xlsx", "description": "Смета", "signed": true},
    {"description": "План", "pages": 3}  // без file генерируется PDF-заглушка
  ],
  "include_pdf": true                   // только gosedo: положить текст как enclosure_document.pdf
}
```

Если коды справочников не входят в набор из эталонов (DK00000000, DK00000073, DP00000077,
DP00000018, DC00000000, DC00000001, LT00000000), укажите их объектом с `id` и `name`.

### Типы пакетов

**document.**
- 2.7.1: `notify_sent: {"need_registration": true, "need_execution": false}` добавляет в
  message.xml уведомление «Поставлен на контроль», как в эталоне ЦП.
- 3.0: `with_digital: true` кладёт digital.xml с событием «Регистрация документа» (как в
  эталоне «ДЭВ с digital»). `container: "gosedo"` переключает пакет на ТК ГосЭДО.
- 2.7 и 2.6: `notify_sent` не поддерживается (в схеме уведомление нельзя приложить к
  документу) и пропускается с предупреждением.
- 2.6: `sign_files: true` добавляет к каждому файлу подпись `<имя>.sig` и signedData в document.xml.

**gosedo** (только 3.0). Создаёт digital.edc.zip, в котором лежат digital.xml и
enclosure_*. Паспорта ТК в этом контейнере нет.

**citizen_appeal.** Заполните `citizen`: `last_name`, `first_name`, `middle_name`, `email`,
`phone`, `number`, `date`, `address` (поля Region, Town, Comment и другие), `rubrics` и
`appeal_file` (файл обращения; без него создаётся заглушка).

**receipt.**
- 2.7.1: `{"accepted": false, "error_code": 3, "comment": "..."}`.
- 2.7 и 2.6: то же без `error_code` (в схеме его нет).
- 3.0: `{"accepted": false, "reasons": [{"id": "102", "comment": "..."}]}`. Коды 101–303
  взяты из приказа 611/96. Для оператора, обслуживающего несколько участников, есть
  `accepted_on` и `rejected_on`.

**notification**, поле `kind`:
- 2.7.1: `registered` (number, date), `refused` (reasons — коды Cat01-004-00005),
  `executor_assigned` (secretary/manager/executor), `report_prepared` (signatory),
  `report_sent` (report), `course_changed` (text), `published` (number, publication_point),
  `sent`.
- 2.7 и 2.6: те же виды, кроме `sent`. У `refused` в схеме одна причина из перечня
  reasonForRejection: указывается код (103–211) или текст причины; если причин несколько,
  берётся первая с предупреждением.
- 3.0: `registered` и `refused`. Пакет уходит как ТК ГосЭДО с событием Exc01-004-00001.

**assignment.**

```json
"assignment": {
  "event": "issue",
  "author": {"name": "Чернышенко Дмитрий Николаевич", "id": "1"},
  "items": [{"number": "5", "text": "...", "deadline": "today+90",
             "executor": "minsport", "coexecutors": ["minenergo"]}],
  "new_deadline": "today+150",          // change_deadline
  "remarks": "...", "fix_deadline": "today+30"   // return
}
```

Если `to` не задан, получателями становятся все исполнители и соисполнители. Для 3.0
`container: "gosedo"` отправляет событие в ТК ГосЭДО.

## Подписи

По умолчанию все .p7s — настоящие отсоединённые подписи CMS/PKCS#7 (DER, SHA-256, RSA),
сделанные ключом встроенного тестового сертификата «MEDOGEN TEST SIGNER - NOT FOR
PRODUCTION» (medogen_core/cms.py). По формату они проходят проверку (в том числе проверочный
бот МЭДО), но сертификат самоподписанный и не ГОСТ, поэтому СЭД, которая проверяет доверие к
сертификату, их отклонит.

digital.xml исходящего документа 3.0 (ДЭВ) не содержит `doc:ПодписиДокумента`, как эталон
«ДЭВ с digital» и реальные пакеты ГосЭДО: подпись документа передаётся файлом document_sign_*.p7s.
В ТК ГосЭДО файлов подписи нет, поэтому подпись документа там идёт в `doc:ПодписиДокумента`,
а если в digital.xml есть «РегистрацияДокумента», добавляется подпись контейнера
`/Документ/Signature` (enveloped, как в эталоне ЦП «Выдача поручения»; показатель 10.7 бота).
В digital.xml поручений (ЦП) есть XMLDSig, как в эталонах ЦП: она подписана тем же тестовым
RSA-сертификатом (сертификат и значения корректно разбираются), но без канонизации и ГОСТ
криптографическую проверку не пройдёт.

В 2.7.1 в ТК добавляется подпись ТК (`containerSignature`, файл container_sign.p7s).
Отключить её можно настройкой `"container_signature": false` в settings.

Настоящие подписи можно получить двумя способами.
- Указать готовые файлы: `signature_file`, `stamp_file`.
- Задать внешнюю команду в `settings.sign_command`, например КриптоПро:

```
"sign_command": "cryptcp -sign -thumbprint <отпечаток> -der -detached -nochain \"{in}\" \"{out}\""
```

  `{in}` — подписываемый файл, `{out}` — куда записать подпись. Подпись ТК 3.0
  (_tk_signature.p7s) ставится на passport.xml и файлы из списка integrity по порядку.
  Подпись XMLDSig внутри digital.xml команда не создаёт.

## Штампы

Картинки штампов собираются с данными документа, как в эталонах 3.0 «ДЭВ без digital» и
2.7.1 «Входящее письмо» (форматы 3.0, 2.7.1 и 2.7; в 2.6 картинок штампов нет).

- Штамп ЭП: «ДОКУМЕНТ ПОДПИСАН ЭЛЕКТРОННОЙ ПОДПИСЬЮ», «СВЕДЕНИЯ О СЕРТИФИКАТЕ ЭП», серийный
  номер, владелец и срок действия. Сведения читаются из сертификата внутри подписи, которая
  легла в пакет: тестовой, от `sign_command` (КриптоПро) или из `signature_file`. Владелец —
  фамилия (SN) и имя отчество (G) сертификата, если их нет — CN. У встроенного тестового
  сертификата владельцем пишется ФИО подписанта из сценария. Если подпись не разобрать,
  на штампе ФИО подписанта и прочерки.
- Штамп регистрации: «ДД.ММ.ГГГГ № номер», при наличии `links` вторая строка
  «На № … от …» по первой связи.
- Пропорции картинки совпадают с размерами штампа в паспорте (`stamp`, `reg_stamp`, w×h в мм).
- `stamp_file` и `reg_stamp_file` по-прежнему подставляют свои картинки вместо собранных.

Текст рисуется без сторонних библиотек: глифы шрифта DejaVu Sans лежат в
medogen_core/font_data.py (пересобрать: `python tools/make_font.py`, нужен Pillow).

## Проверки

После сборки каждый пакет проверяется:
- message.xml и passport.xml по XSD (папка xsd, нужен lxml);
- в 3.0 ровно один `receivers`;
- integrity совпадает с составом архива, passport.xml идёт первым, далее файлы по ASCII;
- файлы, на которые ссылается паспорт, есть в архиве;
- файлы из envelope.ini есть в папке;
- состав ТК ГосЭДО;
- в [ФАЙЛЫ] перечислены все файлы папки пакета (лишний файл бот МЭДО считает ошибкой);
- файлы .p7s/.sig похожи на CMS/PKCS#7;
- обязательные реквизиты заполнены (medogen_core/required.py, работает и без lxml): msgUid,
  отправитель и получатели с GUID и наименованием, created с часовым поясом, docUid ≠ msgUid,
  вид/место/гриф документа с кодом, рег. номер и дата автора, подписант, адресаты, тип заголовка
  и уведомления 2.7.1; все UUID в нижнем регистре; файл ТК указан в [ФАЙЛЫ];
- сверка с ГАС, как в проверочном боте МЭДО (если загружен полный справочник): адреса
  [АДРЕСАТЫ] есть в ГАС и активны, GUID и наименование отправителя совпадают с ГАС, адрес каждого
  получателя есть в [АДРЕСАТЫ]. Расхождения выводятся предупреждениями.

Командой `validate` можно проверить пакет, выгруженный из СЭД; на вкладке «Пакеты» те же
проверки показываются в карточке загруженного пакета («Сверка с ГАС» — отдельным блоком).

В форме интерфейса обязательные поля отмечены *. Пустые обязательные поля подсвечиваются,
список того, что нужно заполнить, выводится над кнопкой «Собрать пакет», и пакет не собирается,
пока они не заполнены. Поля с подсказкой («авто», ФИО по умолчанию) можно оставлять пустыми.

## Тесты

`python -m unittest discover -s tests -v` (или run_tests.bat). Каждое замечание проверочного
бота МЭДО закрепляется тестом в tests/test_bot_findings.py (номер показателя в имени теста):
сначала тест, который воспроизводит ошибку из отчёта бота, затем исправление.

## Допущения (сверить с требованиями получателя)

1. **3.0, уведомления о регистрации и отказе.** XSD процесса Exc01-004-00001 и эталонов этих
   уведомлений в материалах нет. Структура собрана по таблице 2 Типового регламента ГосЭДО.
   Коды событий взяты по порядку из таблицы 1: Event0002 «Регистрация входящего»,
   Event0003 «Отказ в регистрации». Их можно переопределить через
   `notification.event_code`.
2. **3.0, обращение гражданина.** Формат 3.0 не предусматривает CardInfo.txt. Данные автора
   вкладываются приложением `enclosure_cardinfo.txt`.
3. **2.7.1, имя паспорта ЭС.** Используется message.xml; в эталоне ЦП он называется
   container.xml. Имя меняется через `settings.message_file`.
4. **Адреса МЭДО** в orgs\default.json и gas\gas.json взяты из ГАС ГосЭДО от 20.10.2026.
   Бот МЭДО сверяет адрес в envelope.ini с ГАС по GUID получателя, поэтому периодически
   обновляйте справочник ГАС.
5. **Причины отказа в квитанции 3.0** берутся из базового перечня приказа 611/96 (101–303).
   Полный справочник Cat02-001-00002 из сервиса НСИ в материалах отсутствует.
6. **Подпись ТК в 2.7.1** (containerSignature) подписывает passport.xml и остальные файлы ТК
   в порядке ASCII, по аналогии с integrity в 3.0. Состав подписываемых данных для 2.7.1 в
   материалах не описан.
7. **События исполнителя по поручениям** (направление доклада и т.п.) не реализованы,
   потому что в эталонах их нет.
8. **Тип связи ответного документа** — «Связан с» (LT00000000): других значений справочника
   типов связей в материалах нет. Для ТК ГосЭДО связь не добавляется. В 2.6 ответ на документ
   связывается типом «В ответ на» (перечень linkType схемы 2.6).
9. **2.6: подписи файлов по умолчанию не прикладываются** — в эталонах 2.6 их нет. Включаются
   `sign_files: true` (в интерфейсе — флажок).
10. **Версии ниже 2.6** собираются по структуре 2.6 с другим значением `version`. Отдельных
    схем 2.0–2.5 в материалах нет; проверка идёт по схеме «message 27 и 26».
11. **ТК 2.7: версия 2.7 и подпись ТК.** В эталонах 2.7 у паспорта ТК version="1.0" и нет подписи ТК,
    но проверочный бот такие пакеты отклоняет (показатели 3.3 и 3.13), поэтому генератор пишет
    version="2.7" и добавляет container_sign.p7s. Входящий ТК 2.7 с версией 1.0 проверка помечает ошибкой.
12. **2.6: оценка бота ниже по самому формату.** Документ 2.6 передаётся без ТК, поэтому бот
    всегда ставит 0 за показатели 3.1 и 3.2 и коэффициент 0,5 за 2.3 (у 2.7 — 0,75).
